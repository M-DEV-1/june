ORA memory architecture — working design, 2026-07-24

You have two lives.
Your memory shouldn't blur them.

ORA already remembers everything — every window, every scene, every thread. The problem was never capture. It's that one flat keyword index treats a Slack thread about a production incident and a Tuesday-night episode of a show as the same kind of fact, ranked in the same list. This deck is the design for fixing that: a hybrid lexical + semantic retriever, aware of which life a memory belongs to.

01 — what's already there

The tree already exists. It just isn't tagged.

ORA's capture writes into a temporal tree — user → day → session → task → summary — plus a flat episodes table of raw captures, and side tables for threads (a show, a project) and notes (stable facts). Every leaf already carries an app and window title. That's enough signal to know, at write time, which life a memory belongs to — nothing new needs to be captured, only labelled.

02 — the retrieval core

Two rankings, fused once, per question.

FTS5/BM25 is exact-term matching — it wins when the question shares words with what's stored. A vector index wins on paraphrase — "that CUDA rabbit hole" finding an episode titled differently. Neither should replace the other for ORA's corpus size. Reciprocal Rank Fusion runs both independently and merges by rank, not by score — BM25 and cosine distance don't share a scale, so blending scores directly is a false precision. Every item gets Σ 1 / (k + rank) across whichever list(s) it appears in.

Worked example · k = 50

"CUDA out of memory fix" — rank 1 lexical, rank 2 vector1/51 + 1/52 = 0.03884
"that GPU rabbit hole" — rank 1 vector only, absent from lexical1/51 = 0.01961
"cuda toolkit install" — rank 2 lexical only, absent from vector1/52 = 0.01923

The item both retrievers agree on wins outright, even though neither ranked it above every one of its own top hits — that's RRF's "consensus" property, not a coincidence of this example. A lower k (ORA's small corpus favors ~40-60 over the textbook default of 60-100) sharpens this gap further; a much higher k would flatten all three scores toward each other.

03 — choosing the vector index

Why chromem-go, not HNSW — for ORA specifically.

HNSW exists to make search sub-linear on corpora with millions of vectors. ORA's own pruning plan caps the active graph at ~10k nodes. At that size, brute-force cosine search is a few milliseconds — the complexity HNSW adds has no payoff here, and it brings a real cost: coder/hnsw has no internal locking, and its one open concurrency issue is triggered by re-adding an existing key — exactly what happens every time ORA re-embeds an edited note or thread.

For ORA's casecoder/hnswchromem-go
Search at n ≈ 10,000 (the pruning cap) O(log n) — built for millions, unneeded here O(n·d) brute force — low single-digit ms
Recall quality approximate — can miss true neighbors exact
Re-embedding an edited note/thread open panic on key re-add (issue #15) built for concurrent add
Metadata filter (needed for domain tag, §04) none — build it yourself built in
Persistence custom Export/Import wiring gob-based, built in
Constraint fit both pure Go, zero CGO, no external server — either honors ORA's thin-binary rule

Revisit HNSW only if the corpus genuinely outgrows the pruning cap and profiling — not intuition — shows linear scan as the bottleneck.

The coder/hnsw panic itself looks genuinely fixable — it traces to the "elevator" layer-descent pointer not being invalidated on a duplicate-key re-add, not something structural. Worth attempting as an upstream contribution eventually; it just isn't on the path to shipping this harness, since chromem-go already sidesteps it entirely.

04 — two lives, one tree

Domain is a boost, not a wall.

Don't build a second hierarchy next to the temporal tree — tag the nodes it already writes. App and window title are known at capture time; a small lookup classifies most of them without any model call. Ambiguous signal (a browser tab, an untitled terminal) stays untagged rather than guessed wrong.

Boost by default: a mis-tagged episode still surfaces, just lower. Hard filter only when the caller — the model, given an explicit domain argument — is confident enough to ask for one life only.

// classify is a lookup, not a model call — cheap enough to run on every write.
func classify(app, title string) Domain {
    switch {
    case matches(app, workApps) || matches(title, workTitles):
        return DomainWork      // Slack, Calendar, VS Code, terminals, ...
    case matches(app, personalApps):
        return DomainPersonal  // Netflix, Steam, Instagram, ...
    default:
        return DomainUnset     // ambiguous — no boost, no penalty either way
    }
}

Deliberately not an ML classifier: a wrong guess from a model is silent and confident, a lookup-table miss is DomainUnset — visible, and safe by construction, since unset just means "no boost either direction," never a hard exclusion.

Episode raw textbounded — 24h aging ticker, 10-day/0.3-importance floor
Episode row countNOT bounded — rows kept forever, ~110k rows @ 3yr / ~100 per day
NotesNOT bounded — exact-string dedup only, no paraphrase reconciliation
Vector index @ 10k cap, 3072d (full quality)~123-150MB resident — not yet built
Vector index @ 10k cap, 768d (MRL-truncated)~31-40MB resident — some quality cost

Updated stance: RAM/binary size is a "keep it lean where free" preference for ORA, not a hard ceiling — it never overrides retrieval quality. MRL truncation trades some real recall quality for RAM, so the default should favor higher dimensionality (1536 or full 3072) unless actual usage data shows the vector layer costing more RAM than it's worth. Truncate later, measured, if needed — don't pre-shrink against a budget nobody required.

Three mechanisms, one fused ranking, one tool call each time — query_memory/recall never expose which leg answered. That's the hybrid harness: master of the exact match, the association, and the paraphrase, instead of one index straining to be good at all three.

A fourth case worth naming, since it's the one that breaks a purely lexical or purely vector system in opposite ways: "did I already look into this?" asked about something genuinely novel. Lexical returns nothing (correct — it's new). Vector alone can return a false-positive nearest-neighbor from something merely adjacent (a different GPU topic, say) and state it with unwarranted confidence. RRF's fused rank naturally demotes a lone, weak vector hit that lexical doesn't corroborate — this is the same "consensus" property from §02's worked example, just protecting against a false positive here instead of surfacing a true one.

08 — what this changes, concretely

Same tools. Better-informed answers.

No new tools for the model to learn. query_memory and recall keep their shape, gain one optional domain argument, and return results fused from two retrievers instead of one. The temporal tree, the episodes/threads/notes split, and the Retriever interface all stay exactly as they are — this slots in behind them.

hybrid = RRF(FTS5, chromem-go) · domain = boost by default, filter on request · embeddings = gemini-embedding-2-preview, full dimensionality by default · no new external services
