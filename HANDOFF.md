## What the system is right now

A Go daemon (`./ora --daemon`, port 6942, localhost only, CGO_ENABLED=0 always) that captures the user's Linux desktop into a layered memory (episodes → summaries → threads → personal context, sqlite FTS + chromem vectors with a local EmbeddingGemma llama-server on port 6943), records and transcribes meetings locally (whisper.cpp Vulkan, `-dev 1`), talks by voice (Gemini Live 2.5 native audio) and is proactive: evening close + first-person diary (after 22:00), morning brief (first activity after 9:00), meeting prep (on recorder start), and overnight dreaming.

Brains are per-duty via `internal/brain` (`Brain func(ctx, prompt) (string, error)`): writing duties = claude-cli sonnet, dream judge = grok-cli (curfew-exempt), dream shadow = local Gemma-4 E2B Q2 via llama-server on port 6944 pinned to `-dev Vulkan1`, judges/evals = gemini flash. Usage doctrine: no Claude call may open a usage window between 03:25 and the user's deliberate 08:30 session start; the brief and the Sunday study pass ride the user's window; dreams cost zero Claude.

## What happened 2026-08-31 → 09-01 (committed to branch `today`, stacked on `restore-green-and-autostart`; 19 packages green)

The arc: a morning complaint about meeting minutes turned into finding why Ora's memory could not answer questions about itself.

**The finding.** `internal/db/search.go`: `const maxEpisodeExcerpt = 200`, and every caller passed `0` meaning "use the default" — `query_memory`, the live session's context injection, and the eval. Every memory row any model ever saw was cut to 200 runes; ten hits gave the model ~2,203 characters as its whole view of two months. The name is the diagnosis: sized for episodes, then notes/threads/summaries and 2,456–7,294-character meeting minutes joined the same search path and inherited an episode's budget. Truncation happens *after* retrieval succeeds, so from outside it is indistinguishable from retrieval failing — which is what it had been called for months. Fixed by `excerptBudget(source)`: episode 200 (unchanged), thread/summary 700, note/diary 4000. **Both `FormatHit` and `FormatNoteHit`** — `query_memory` routes notes to the latter, and budgeting only the former left the live agent unchanged while the eval reported success (caught in review, fixed, test at `hybrid_test.go::TestFormatNoteHit_GetsTheSameBudgetAsFormatHit`).

**Four more of the same shape** — data that exists, destroyed between the store and the model:
1. `FormatHit` rendered `Mon Jan 2` — the date without the hour — so every question about time of day was unanswerable from any number of rows. Now `Mon Jan 2 15:04`.
2. 261 threads and 4,901 episodes had **no edge**, though the compiler computes the attribution on every flush and discarded it (`if _, err := store.WriteEpisode(...)` in the daemon's event loop dropped the id). Added `episode_threads`, written by `LinkEpisodesToThread` using the buffer's own time span, plus a `thread_evidence` tool. Fills forward only; existing episodes stay unlinked.
3. The agent could write action items (`update_action`) but not read them, so "what do I owe" went through semantic search and returned summaries *about attending meetings*. Added `action_items`.
4. Meeting capture: the transcript rendered as **one 21,158-character paragraph** for thirty minutes (`renderTranscript` merged same-speaker segments unbounded — now `breaksTurn` on `>>`, a 2s silence, and a one-minute ceiling); whisper **echoed its own priming prompt** into the transcript as speech, with participant names scraped from a WhatsApp tab; and the meeting window was **never captured at all** because the tracker read only the focused window. See `internal/tracker/CONTEXT.md`.

**Diarization is real.** sherpa-onnx offline speaker diarization at `~/.local/share/ora/sherpa` (pyannote segmentation + wespeaker CAM++, ONNX, no Python), run on `system.wav` only — the mic is one known person by construction. `internal/recorder/diarize.go`. Threshold is a config knob because no value transfers between meetings.

**Track 8 — context vs capacity** (`evals/track8_capacity.go`). Scores two axes against the same frozen rows: a judge says whether the rows were sufficient; three model families (claude-sonnet, grok, agy, all on subscriptions) answer from those exact rows and are judged on what they said. `evals/probes.jsonl` holds 25 probes built by reading the database, each carrying an `expect` never shown to any judge. See `docs/evals.md`.

**What it found.** Retrieval is at **9/18** on questions designed to be answerable. And the reframing result: with refusal measured separately from correctness, claude answered 14 and over-refused 4; grok answered 10 and over-refused 8 — both totalling 18. **Neither gave a single wrong answer.** Ora's failure mode is silence, not hallucination, which a single accuracy number renders identically to being wrong.

**Two operational facts.** `cmd/daemon.go` and `evals/main.go` read the same `GEMINI_API_KEY`: the memory compiler and the eval judge share one free-tier quota, so **measuring Ora degrades Ora** — three runs exhausted it and `AttributeThreads` began failing 429 silently, because the compiler falls back and keeps going. Fix is to move the compiler onto `brain.FromConfig` (already claude-cli here). And the machine reboots with autostart, so a stale daemon can be running a binary older than the tree — check `ps -o lstart` against the binary's mtime before believing a live test.
